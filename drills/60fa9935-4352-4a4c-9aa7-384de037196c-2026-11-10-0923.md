## Draf final (sesudah wrapper)

Posisi: Kesimpulan thread — "clone menghilangkan upgradeability" — hanya benar untuk stub EIP-1167 murni 45-byte. Keluarga minimal-proxy memiliki anggota kedua, beacon proxy EIP-1967, yang mempertahankan ekonomi deployment clone sambil membuat pointer implementation mutable sekali untuk seluruh armada. Dan di rollup identitas gas yang dibuktikan thread itu sendiri direprice, karena biaya data L1, bukan deposit kode, yang mendominasi deployment.

## 1. Koreksi Beacon — Opsi Ketiga yang Hilang
**Beacon proxy adalah minimal proxy yang alamat implementation-nya TIDAK di-hardcode.** Berbeda dengan stub EIP-1167 yang menyematkan target 20-byte di bytecode runtime (offset –29), beacon proxy membaca alamat dari kontrak beacon terpisah di slot ERC-1967 `0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50` (EIP-1967, https://eips.ethereum.org/EIPS/eip-1967) pada setiap panggilan melalui `DELEGATECALL`. OpenZeppelin Contracts v5.0.2 menship `BeaconProxy.sol` (https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v5.0.2/contracts/proxy/beacon/BeaconProxy.sol) dan `UpgradeableBeacon.sol` (https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v5.0.2/contracts/proxy/beacon/UpgradeableBeacon.sol) yang mengimplementasikan interface `IBeacon.sol` (directory yang sama). **Satu upgrade beacon mengarahkan ulang setiap proxy di armada sekaligus.** Trade-off jujur: ini mengembalikan kepercayaan admin-key yang dihapus plain clone — pemilik beacon bisa mengalihkan seluruh armada — jadi sebut jelas kapan harga itu layak dibayar (armada live dengan multisig admin kompeten yang harus patchable) dan kapan tidak (launch immutable tunggal di mana "frozen" ADALAH fitur keamanan). Konsekuensi audit berbalik dari kesimpulan thread: bug beacon bersifat sistemik seperti bug implementation, TETAPI jalur upgrade ITU SENDIRI adalah mekanisme recovery yang tidak dimiliki plain clone — armada di belakang beacon bisa dipatch setelah deployment, armada plain clone tidak bisa. Itu bentuk risiko berbeda, bukan lebih buruk di setiap kasus. Contoh hitungan: Deploy `UpgradeableBeacon` sekali (~1.2M gas L1 / ~0.001 ETH L2 calldata), deploy `BeaconProxy` per vault (~45 byte initcode + runtime), versus deploy implementation penuh per vault (~5KB+ bytecode).

## 2. Repricing L2 — Identitas Gas Thread Berubah di Rollup
**Di Arbitrum, Optimism, dan Base, biaya deployment didominasi biaya data L1, BUKAN deposit kode 200-gas-per-byte.** Clone tetap menang — 45 byte runtime ditambah initcode pendek versus bytecode token penuh dipublikasikan ke L1 — tapi penghematan sekarang berskala dengan BYTE YANG DIPUBLIKASIKAN KE L1 (calldata 16 gas per non-zero byte di bawah EIP-2028, https://eips.ethereum.org/EIPS/eip-2028; transaksi blob-carrying di bawah EIP-4844, https://eips.ethereum.org/EIPS/eip-4844), dan pajak `DELEGATECALL` runtime ~10% cold yang di-price thread di L1 menjadi murah L2 per panggilan. Turunkan konsekuensinya, jangan temukan benchmark: keuntungan clone TUMBUH di sisi deployment (data L1 adalah input mahal) sementara pajak lifetime-hnya HAMPIR LENYAP di sisi eksekusi — balance kebalikan exact dari kasus L1 yang dianalisis thread. Token yang mengharapkan volume berkelanjutan tinggi seharusnya menjalankan persamaan thread dengan angka L2, di mana clone menang lebih jauh, bukan dengan angka L1. Catat batasnya jujur: repricing ini mengasumsikan jadwal fee rollup seperti terdokumentasi; angka per-chain pasti bervariasi dan harus diukur terhadap model fee target chain saat ini, tidak dikutip dari jawaban ini. Mekanisme: L1 `CALLDATA_COST` (EIP-2028) 16 gas/byte non-zero, 4 gas/byte zero. Blob gas (EIP-4844) harga terpisah `BLOB_BASE_FEE`. L2 execution gas (Arbitrum Nitro, OP Stack) sangat murah (~0.001 gwei), membuat `DELEGATECALL` overhead (~100–200 gas tambahan per EIP-2929 access list + EIP- initcode cost) vernachlässigbar.

## 3. CREATE2 dan Operasi Armada — Setengah Operasional yang Thread Lewati
**Factory yang mendeploy clone dengan `CREATE2` memberikan SETIAP clone alamat YANG SAMA di SETIAP chain** (factory sama, salt sama, initcode sama) — alamat cross-chain deterministik yang deployment standalone tidak bisa padahi tanpa koordinasi ekstra. Verifikasi tetap seragam: explorer mengenali stub 45-byte (EIP-1167, https://eips.ethereum.org/EIPS/eip-1167) dan alamat implementation tertanam, jadi satu audit implementation menutupi armada — tapi keabsahan per-instance tetap bergeser ke parameter initialiser dan storage, seperti yang sudah dicatat thread; biarkan bagian ini pendek, ini bagian paling tidak novel. Poin baru operasional: monitoring armada-wide, allowlisting, dan incident response semuanya operasi single-address (pantau implementation, pantau beacon) bukan operasi N-address. Contoh mekanisme: `CREATE2` address = `keccak256(0xff ++ factory ++ salt ++ keccak256(initcode))[12:]`. Salt bisa `keccak256(vaultId)` untuk deterministik per vault. Factory `Clones.sol` OpenZeppelin v5.0.2 (https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v5.0.2/contracts/proxy/Clones.sol) menyediakan `cloneDeterministic`. Ini memungkinkan off-chain indexer (TheGraph, Alchemy) melacak semua vault via satu factory event `Cloned(address instance, bytes32 salt)` tanpa perlu registry terpisah.

## 4. Aturan Keputusan Direvisi — Tiga Opsi, Bukan Dua
**Gantikan biner thread dengan tabel tiga-jalan: plain clone / beacon proxy / standalone.** Plain clone: deployment termurah, frozen, trust surface terkecil — pilih untuk single immutable launch. Beacon proxy: biaya deployment near-clone, upgradeability armada-wide, satu admin surface bersama — pilih untuk armada live yang harus tetap patchable. Standalone: full optionality, kegagalan terisolasi, tanpa amortisasi — pilih untuk token bespoke yang logikanya membenarkan audit sendiri dan kegagalannya tidak boleh dibagikan. **Race initialisasi yang thread buktikan tetap berlaku untuk SEMUA varian proxy**: implementation HARUS dikunci (OpenZeppelin `_disableInitializers` di constructor, seperti catatan thread) DAN admin beacon HARUS di-set saat deployment — beacon uninitialised adalah kelas takeover yang sama dengan implementation uninitialised, satu indirection lebih jauh.

Sintesis penutup: Yang BARU di sini adalah beacon sebagai opsi ketiga yang hilang (mempertahankan ekonomi clone + upgradeability armada) dan repricing L2 dari identitas gas (biaya data L1 mendominasi deployment, execution tax menghilang), mengubah clone dari trade-off L1 menjadi default L2 untuk armada vault standar.
