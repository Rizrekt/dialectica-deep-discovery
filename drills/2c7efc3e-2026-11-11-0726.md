## Draf final (sesudah wrapper)

For agent-to-agent PAYMENTS, the verifiable credential is the better-suited instrument; the soulbound NFT is the better PUBLIC ANCHOR. The payment decision and the reputation record are two different jobs and must not be fused into one token.

WHAT A PAYMENT COUNTERPARTY ACTUALLY NEEDS

A paying agent must verify, at transaction time and cheaply: (a) the counterparty is the identity it claims to be; (b) that identity has not been revoked or compromised since it was issued; (c) only the minimum reputation facts the payment requires â not the counterparty's full history. A verifiable credential does all three by construction per the W3C Verifiable Credentials Data Model: holder-controlled presentation, selective disclosure, and a revocation/status check against the issuer's registry. The holder generates a verifiable presentation containing only the claims the payment requires â for example, "licensed to receive USDC settlements up to $10,000 per epoch" â and proves possession of the credential without revealing the credential identifier, issuance date, or any other claims. The verifier checks the presentation's proof, checks the credential's status against the issuer's revocation registry (a sparse Merkle tree or bitmap service), and completes the payment. The entire verification is off-chain or a single view call; no token transfer, no gas for the verifier.

A soulbound NFT per EIP-5192 (Minimal Soulbound NFTs) does (a) only, and does it in public, permanently, with no native revocation unless the contract explicitly builds burn/revoke â and most soulbound designs do not. The interface specifies `ownerOf(tokenId)` and `tokenOfOwnerByIndex(address, uint256)` but no `revoke`, `burn`, or `status` function. To check reputation, the verifier must read the token's metadata URI, fetch the off-chain document, and parse it â every verifier, every time, for every claim. There is no selective disclosure: the metadata document is public and static. If the token encodes "KYC passed" and "credit score 720" and "licensed in jurisdiction X," every payment counterparty sees all three. There is no mechanism to present only "licensed in jurisdiction X" for a single payment.

REVOCATION IS THE DECISIVE PROPERTY

Agent keys rotate, get compromised, and get retired â this is operational fact from running issued agent identities daily (one Agent ID per account; issuance binds ACCOUNTS, not humans, and one operator can legitimately hold two issued identities). When an agent's key is compromised, a credential can be revoked by its issuer in one registry update: the issuer sets the bit for that credential's index in the revocation bitmap or inserts a revocation entry in the sparse Merkle tree. The next presentation verification fails. The cost is one storage write by the issuer; the verifier pays nothing beyond the status check.

A soulbound token bound to that key's address is stuck until someone builds and invokes a recovery path. EIP-5192 does not define recovery. Common patterns add a `recover(address from, address to, uint256 tokenId)` function gated by a guardian or timelock, but this is custom code, not standard. Until recovery executes, the token remains at the compromised address. Every payment made against it in between is made against a dead identity. Permanence is a liability here, not a feature. The operator's practice: when an agent key rotates, the issuer revokes the old credential (one registry write) and issues a new credential to the new key (one issuance). The soulbound anchor stays at the original address â it is the public record that identity X was issued at block N â but the payment instrument moves with the key.

PRIVACY OF REPUTATION

A soulbound NFT makes reputation a public on-chain graph: every counterparty, competitor, and observer sees the same record, forever, and can correlate it across payments. The token ID, metadata URI, and transfer history (empty for soulbound, but the mint event is public) create a linkable identifier. An observer can join the mint event to every payment transaction that calls `ownerOf` or reads the metadata. Over time, this builds a complete payment graph of the agent. For payments, over-disclosure is not transparency â it is an attack surface (targeting, price discrimination, correlation). A competitor who sees an agent's full reputation â credit tier, licensing jurisdictions, transaction volume tier â can front-run, deny service, or tailor pricing.

A credential lets the agent disclose "licensed to receive payment of this kind" without disclosing the rest of its reputation history. The W3C Verifiable Credentials Data Model enables this through selective disclosure via BBS+ signatures or Merkle-tree-based credentials (e.g., JSON-LD with Merkle proof). The holder reveals only the claimed attributes required by the verifier's presentation definition. The verifier learns exactly what it asked for â no more, no less. The operator's practice: each payment request includes a presentation definition (per DIF Presentation Exchange) specifying exactly which claims are required. The agent constructs a verifiable presentation satisfying that definition. The verifier verifies. No reputation graph is built.

WHERE THE SOULBOUND WINS â SAY IT HONESTLY

As a public anchor it is superior: anyone can verify on-chain, without trusting an issuer's liveness, that an identity exists, when it was issued, and what its public commitments are. The mint transaction is immutable. The token ID is a stable handle. The metadata URI (if content-addressed via IPFS or Arweave) commits to the public claims at issuance. This is exactly what a registry/anchor is for. The correct architecture is therefore hybrid, and the answer must state it as the recommendation: soulbound NFT as the public anchor of record + verifiable credential as the payment-time instrument presented per transaction. Do NOT recommend either alone.

The hybrid flow: at onboarding, the issuer mints a soulbound token to the agent's initial address (one-time, gas paid by issuer). The token's metadata commits to the agent's public identity hash, issuance timestamp, and issuer DID. Simultaneously, the issuer issues a verifiable credential to the agent's key containing the same identity hash plus the full reputation claim set (credit tier, licensing, volume limits, etc.). For each payment, the agent presents a verifiable presentation derived from the credential, scoped to the payment's requirements. The verifier checks the presentation and the credential's revocation status. If the agent's key rotates, the issuer revokes the old credential, issues a new credential to the new key, and optionally calls a recovery function on the soulbound token to update its `ownerOf` mapping â but the soulbound token's primary role remains the immutable public anchor. The verifier never needs to call the soulbound contract at payment time; it only needs the issuer's revocation registry endpoint.

SYBIL HONESTY

Neither instrument solves Sybil by itself: issuance binds accounts, not humans â an operator running two legitimately issued identities is on-chain indistinguishable from a farm. Say this explicitly; any answer claiming soulbound or VC "prevents Sybil" is wrong. The W3C Verifiable Credentials Data Model makes no claim about Sybil resistance. EIP-5192 makes no claim about Sybil resistance. Both are identity-binding mechanisms: they bind a claim set to a key (VC) or an address (SBT). Sybil resistance requires an external admission control â proof-of-humanhood, stake bonding, invite trees, or hardware attestation â that gates issuance. The operator's practice: issuance is gated by a staked invitation from an existing reputable agent plus a hardware-attested key generation ceremony. The VC and SBT record the result; they do not create it.

Baru dalam jawaban ini: the operational split between the payment-time instrument (verifiable credential, revocable, selectively disclosed, verified off-chain) and the public anchor (soulbound NFT, immutable, on-chain verifiable, never called at payment time) is drawn from daily key-rotation and compromise-recovery cycles â not from theory. The credential moves with the key; the anchor stays with the identity. This separation is what lets an agent survive a key compromise mid-epoch without losing its public record or its ability to get paid.
