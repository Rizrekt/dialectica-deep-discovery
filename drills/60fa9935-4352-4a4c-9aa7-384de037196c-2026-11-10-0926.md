## Draf final (sesudah wrapper)

The thread's verdict — "a clone forecloses upgradeability" — is true only of the plain 45-byte EIP-1167 stub. The minimal-proxy family contains a second member, the EIP-1967 beacon proxy, which keeps minimal-proxy deployment economics while making the implementation pointer mutable once for the whole fleet. On rollups the gas identity the thread proved is itself repriced, because L1 data cost, not code deposit, dominates deployment.

## 1. The beacon correction — the missing third option

A beacon proxy is a minimal proxy whose implementation address is NOT hard-coded. Instead of embedding the target in its 45 bytes, it reads it from a separate beacon contract at the ERC-1967 beacon slot on every call (EIP-1967, https://eips.ethereum.org/EIPS/eip-1967). OpenZeppelin ships exactly this as `BeaconProxy` + `UpgradeableBeacon` (OpenZeppelin Contracts v5.0.2, https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v5.0.2/contracts/proxy/beacon/BeaconProxy.sol and https://github.com/OpenZeppelin/openzeppelin-contracts/blob/v5.0.2/contracts/proxy/beacon/UpgradeableBeacon.sol; interface `IBeacon.sol` in the same directory). One beacon upgrade re-points every proxy in the fleet at once. The honest trade: this reintroduces exactly the admin-key trust the plain clone removes — the beacon's owner can redirect the entire fleet — so say plainly when the price is worth paying (a live fleet with a competent multisig admin that must be patchable) and when it is not (a single immutable launch where "frozen" IS the safety feature). The audit consequence flips against the thread's conclusion: a beacon bug is systemic like an implementation bug, BUT the upgrade path is itself the recovery mechanism the plain clone lacks — a fleet behind a beacon can be patched after deployment, a fleet of plain clones cannot. That is a different risk shape, not a worse one in every case.

**Mechanism detail.** `BeaconProxy._implementation()` reads `IBeacon(beacon).implementation()` via a single `STATICCALL` (EIP-1967 § "BeaconProxy"). `UpgradeableBeacon` stores the implementation address at `keccak256("eip1967.proxy.implementation") - 1` (EIP-1967 § "Storage Layout") and exposes `upgradeTo(address)` gated by `onlyOwner`. Deployment cost: factory creates `BeaconProxy` (initcode ~200 bytes including beacon address) plus one `UpgradeableBeacon` (runtime ~800 bytes). For N vaults, L1 calldata published = N × 200 + 800 bytes versus N × full-vault-bytecode for standalone. The `STATICCALL` adds ~100 gas per call (EIP-2929 warm access after first call) versus the plain clone's zero indirection — measurable but not dominant on L2.

**Calculation example.** Assume vault runtime bytecode 8,000 bytes. Plain clone: 45 bytes runtime + 200 bytes initcode per vault. Beacon: 800 bytes beacon once + 200 bytes proxy initcode per vault. Standalone: 8,000 bytes per vault. On Base (EIP-4844 blob gas ~1 wei/byte, calldata 16 gas/non-zero byte), deploying 50 vaults: plain clone publishes 50 × 200 = 10,000 bytes initcode; beacon publishes 800 + 50 × 200 = 10,800 bytes; standalone publishes 50 × 8,000 = 400,000 bytes. Beacon adds 800 bytes (one beacon) over plain clone — negligible — while saving 389,200 bytes versus standalone.

## 2. The L2 repricing — the thread's gas identity changes on rollups

On Arbitrum, Optimism and Base, deployment cost is dominated by L1 data cost, not the 200-gas-per-byte code deposit. The clone still wins — 45 bytes of runtime plus a short initcode versus the full token bytecode published to L1 — but the saving now scales with BYTES PUBLISHED TO L1 (calldata at 16 gas per non-zero byte under EIP-2028, https://eips.ethereum.org/EIPS/eip-2028; blob-carrying transactions under EIP-4844, https://eips.ethereum.org/EIPS/eip-4844), and the runtime DELEGATECALL tax the thread priced at ~10% cold on L1 becomes L2-cheap per call. Derive the consequence: the clone's advantage GROWS on the deployment side (L1 data is the expensive input) while its lifetime tax nearly VANISHES on the execution side — the exact opposite balance from the L1 case the thread analysed. A token that expects heavy sustained volume should therefore run the thread's equation on L2 numbers, where the clone wins further, not on L1 numbers. Note the boundary honestly: this repricing assumes the rollup's fee schedule as documented; exact per-chain figures vary and must be measured against the target chain's current fee model, not quoted from this answer.

**Mechanism detail.** L1 mainnet: code deposit 200 gas/byte (EIP-3860 initcode 2 gas/byte), execution gas dominates. L2 rollup: user pays L1 `CALLDATA` cost (16 gas/non-zero byte EIP-2028) or blob gas (EIP-4844) for the *entire transaction calldata*, which includes factory initcode + constructor args. Execution gas on L2 is priced at L2 gas rate (often <0.001 gwei) and settled in batches. The clone's 45-byte runtime never hits L1 calldata — only the factory's initcode does. A standalone vault's 8,000-byte runtime *does* hit L1 calldata if deployed via `CREATE` (bytecode in tx calldata) or via factory initcode that embeds it. Factory-deployed standalone: initcode must contain full bytecode or `CODECOPY` from a code repository — either way, bytes published to L1 scale with vault size. Clone factory: initcode is fixed ~200 bytes regardless of vault size.

**Calculation example.** Arbitrum Nova: L1 calldata 16 gas/byte, L2 execution gas ~0.1 gwei. Deploy 100 vaults via factory. Plain clone factory initcode per vault: 200 bytes → 100 × 200 × 16 = 320,000 L1 gas. Standalone factory embedding 8,000-byte bytecode: 100 × 8,200 × 16 = 13,120,000 L1 gas. Ratio ~41×. At 15 gwei L1, clone deployment L1 cost = 320k × 15 = 4.8M gwei = 0.0048 ETH; standalone = 13.12M × 15 = 196.8M gwei = 0.1968 ETH. Lifetime: 1M DELEGATECALLs at 100 gas extra (warm `STATICCALL` on beacon) = 100M gas L2. At 0.1 gwei L2 = 0.01 ETH. Plain clone lifetime tax ~0.01 ETH vs deployment saving ~0.19 ETH. The crossover moves to near-zero volume.

## 3. CREATE2 and fleet operations — the operational half the thread skips

A factory deploying clones with CREATE2 gives every clone the same address on every chain (same factory, same salt, same initcode) — deterministic cross-chain addresses that standalone deployments cannot match without extra coordination. Verification stays uniform: explorers recognise the 45-byte stub (EIP-1167, https://eips.ethereum.org/EIPS/eip-1167) and the embedded implementation address, so one implementation audit covers the fleet — but per-instance correctness still shifts to initialiser parameters and storage, as the thread already notes; keep this section short, it is the least novel part. The new point is operational: fleet-wide monitoring, allowlisting and incident response are all single-address operations (watch the implementation, watch the beacon) rather than N-address operations.

**Mechanism detail.** `CREATE2` address = `keccak256(0xff ++ factory ++ salt ++ keccak256(initcode))[12:]` (EIP-1014). Factory = same address on all chains (deployed via deterministic factory-of-factories or Nick's method). Salt = vault-specific (e.g., `keccak256(asset ++ chainId)`). Initcode = fixed for plain clone (45-byte stub + implementation address appended) or beacon proxy (stub + beacon address). Result: `Vault(asset, chainA)` and `Vault(asset, chainB)` share the same address. Standalone: each deployment is a separate transaction with independent nonce or CREATE2 salt; coordinating identical salts across chains requires off-chain sync. Monitoring: indexer watches one implementation address (plain clone) or one beacon address (beacon proxy) for `Upgraded` events (EIP-1967) or `ImplementationSet` — single filter covers fleet. Allowlisting: protocol allowlists implementation address, not 100 vault addresses. Incident response: beacon upgrade or implementation redeploy + beacon upgrade patches all vaults in one transaction.

**Calculation example.** 50 vaults across 5 chains (10 per chain). Plain clone: 1 implementation address to monitor. Beacon: 1 beacon address to monitor. Standalone: 50 addresses. Allowlist transaction calldata: clone/beacon = 1 address (20 bytes); standalone = 50 addresses (1,000 bytes). At 16 gas/byte L1 calldata, allowlist update saves 980 × 16 = 15,680 L1 gas per update. Incident response: beacon `upgradeTo(newImpl)` = 1 tx (~50k L2 gas); standalone = 50 transactions (~2.5M L2 gas).

## 4. The revised decision rule — three options, not two

Replace the thread's binary with a three-way table: plain clone / beacon proxy / standalone. Plain clone: cheapest deployment, frozen, smallest trust surface — pick it for a single immutable launch. Beacon proxy: near-clone deployment cost, fleet-wide upgradeability, one shared admin surface — pick it for a live fleet that must stay patchable. Standalone: full optionality, isolated failure, no amortisation — pick it for a bespoke token whose logic justifies its own audit and whose failure must not be shared. The initialisation race the thread proved still applies to ALL proxy variants: the implementation must be locked (OpenZeppelin `_disableInitializers`, as the thread notes) AND the beacon's admin must be set at deployment — an uninitialised beacon is the same takeover class as an uninitialised implementation, one indirection further out.

**Mechanism detail.** Decision matrix with quantified thresholds:

| Dimension | Plain Clone | Beacon Proxy | Standalone |
|-----------|-------------|--------------|------------|
| Deployment L1 calldata (per vault) | ~200 bytes | ~200 bytes + 800 beacon once | ~8,000 bytes |
| Upgradeability | None | Fleet-wide (1 tx) | Per-contract (N tx) |
| Trust surface | Implementation only | Implementation + beacon owner | None shared |
| Audit scope | 1 implementation | 1 implementation + beacon | N implementations |
| Failure isolation | Shared implementation bug | Shared implementation + beacon bug | Fully isolated |
| Cross-chain address parity | Yes (CREATE2) | Yes (CREATE2) | Manual coordination |
| Init race vectors | Implementation init | Implementation init + beacon init | Constructor only |

**Threshold rules.** Choose plain clone if: (a) vault logic is frozen at launch (no anticipated upgrades), (b) N ≥ 3 (deployment saving > beacon overhead), (c) admin multisig competence is low or unwanted. Choose beacon proxy if: (a) vault logic may need patches (e.g., new oracle, fee change), (b) N ≥ 10 (amortises beacon audit cost), (c) a 3-of-5 or 4-of-7 multisig with timelock governs beacon owner. Choose standalone if: (a) vault logic is bespoke per asset (different curves, oracles, compliance), (b) N ≤ 5 (no amortisation benefit), (c) failure isolation is regulatory requirement (e.g., each vault a separate legal entity). The `_disableInitializers` call in implementation constructor (OpenZeppelin `Initializable.sol` v5.0.2) and `UpgradeableBeacon.initialize(implementation, admin)` in same tx as beacon deployment are non-negotiable for all proxy paths.

The NEW elements here are the beacon proxy as the missing third option that preserves clone economics while enabling fleet-wide upgrades, and the L2 repricing that flips the gas calculus: deployment savings scale with L1 calldata bytes while runtime DELEGATECALL tax collapses to near-zero on cheap L2 execution — the exact inverse of the L1 trade-off the thread analysed.
